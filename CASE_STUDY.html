aretil

A legal experience-management data layer, exposed as an MCP server, that lets Claude answer business-development questions against firm data

The Problem

A law firm's most valuable asset is its own history — the matters it has worked, the clients it has served, the deals its lawyers have led. But this data is trapped:

🔒 Locked in Legacy Architecture

Foundation stores it in a relational, UI-centric schema with no API. No AI agent can reach it without going through a human and a screen.

⏱️ Workflows Are Slow

Drafting a pitch in response to an inbound RFP is hours of analyst work spent finding and summarizing relevant past matters.

🧠 AI Alone Is Insufficient

Claude is excellent at synthesis, but it cannot answer "show me our healthcare M&A deals over $100M where we repped the target" unless something has first structured and entity-resolved that data.

The gap: The missing layer is a structured, entity-resolved firm-data layer that an AI agent can query. This prototype is built to make that thesis tangible.

The Thinking

Why This Approach?

Three facts framed the strategy:

  1. Claude for Legal launched May 12, 2026. Anthropic shipped 20+ MCP connectors (iManage, NetDocuments, Westlaw, Harvey, etc.) — but Litera/Foundation is not on the list. That's the gap we're filling.
  2. Foundation ships no API. Every serious competitor (Intapp DealCloud, others) exposes data programmatically. This is an architectural admission.
  3. The market is underserved. Foundation prices for AmLaw 100; DealCloud is enterprise-only. Mid-market firms (150–500 lawyers) have no credible experience-management product.

Design Philosophy

Single source of truth: SQL macros defined once, reused by both the MCP server and the TypeScript web app. No dual implementations to keep in sync.

Local and lightweight: Runs on a laptop. Only external dependency at demo time is Claude API for drafting.

Inspectable, not black-box: Every tool call resolves to visible SQL. The audience can see how an answer was produced.

Two distinct surfaces on one data layer: Demonstrates platform thinking, not a one-off feature.

Key Architectural Decisions

Decision Rationale Trade-off
DuckDB as substrate Single file, relational + vector search + VARIANT for semi-structured data. No external infrastructure. Limits scalability beyond ~100 matters; no distributed queries.
Splink for entity resolution Probabilistic record linkage on DuckDB. Reconciles "Latham", "L&W", "Latham & Watkins" into one entity at build time. One-time resolution at build; new counsel names require rebuild.
model2vec for embeddings Pure-numpy static model. No PyTorch, no API dependency at build time. 256-dim vectors. Lower quality than larger models, but sufficient for semantic ranking.
SQL macros as tools Define once (in macros/tools.sql), call from both MCP and Node API. Zero risk of drift. Limited tool expressiveness; must work within DuckDB's macro syntax.
Vite for web frontend Minimal, fast, no hidden abstractions. Framework-light for MVP. Manual routing/state; not suitable for large apps.
Regex-based markdown rendering Simple, zero dependencies, works for 80% of use cases. Fragile for edge cases (nested lists, complex formatting). List support removed.

What Worked Well ✅

1. SQL Macros as the Single Source of Truth

Defining tools once in DuckDB and calling them from both MCP and the Node API proved exactly right. Zero implementation drift. Both surfaces answer the same way to the same query.

"The hardest part of shipping two surfaces for one API is keeping them in sync. By making the database the interface, we solved that in the architecture layer, not the process layer."

2. Synthetic Dataset Seeded from SEC EDGAR

Using real company names, industries, and deal structures from SEC filings gave the demo instant credibility. Lawyers recognized the data shapes immediately. The synthetic law firm and timekeepers felt real because everything else was.

3. MCP as an Access Pattern

Using the Model Context Protocol meant Claude could call tools without bespoke integration. Tools showed up in the client's UI automatically. No auth, no rate limiting to reason about — just clean tool definitions and results flowing through the message loop.

4. Splink for Entity Resolution

The Splink pass reconciled 242 party records into 51 canonical entities. The "Latham / L&W / Latham & Watkins" moment — where one query returns all variants — became the differentiator. It's simple, it's visible (the SQL), and it actually works.

5. Two Distinct Workflows on One Data Layer

RFP-to-Pitch and Timekeeper Bio both call the same macros. This immediately reads as a platform, not a wrapper around Claude.

6. TypeScript for the Backup Surface

Having a working web app (port 5173) as a fallback if MCP setup fails was critical. It proved the concept works without Claude Desktop's complexity. Both surfaces are production-ready — MCP is primary, web app is the backup when setup is hard.

What Didn't Work (or Limitations) ⚠️

1. Regex-Based Markdown Rendering

The issue: Simple regex chains for markdown → HTML work for 80% of cases but fail on nested lists, mixed list types, and complex formatting. The greedy pattern for wrapping lists could collapse separate lists together.

Impact: List support was removed from the web app. Pitches render beautifully for headings, emphasis, and paragraphs, but if Claude generates complex nested structures, they might not format correctly.

The fix: Use a proper markdown library (marked.js or remark) for production. Estimated effort: 30 minutes, +15 KB bundle size.

2. Embedding via Subprocess (Python Bridge)

The issue: The MVP calls Python embed_query() via execSync to generate embeddings. This adds ~2–5 seconds of latency per query (Python startup overhead).

Impact: RFP-to-pitch takes ~60–90 seconds, but 5–10 seconds of that is embedding + subprocess overhead.

The fix: Port model2vec to JavaScript (via ONNX.js or Transformers.js). This reduces latency to ~30–50 seconds total. Estimated effort: 2–3 hours.

3. No Real-Time Streaming

The issue: Claude's response is fully generated before the client sees it. There's no token-by-token streaming to show progress.

Impact: Users see a loading spinner for 60+ seconds, then a full pitch appears. No sense of progress.

The fix: Add streaming support to the Node API and wire SSE (Server-Sent Events) to the frontend. Estimated effort: 2 hours.

4. Limited to ~100 Matters

The issue: DuckDB is fast for semantic search over 70 matters, but larger datasets would need optimization (indexing, caching, or a vector database).

Impact: Not a production database for AmLaw firms. This is fine for a PoC, but a real product would need DuckDB tuning or a separate vector DB.

The fix: Add DuckDB vector index support or adopt Pinecone/Weaviate. Estimated effort: 4–6 hours.

5. Entity Resolution Is One-Time

The issue: Splink runs at build time. New counsel names (e.g., a merger creates "Latham + McKinsey LLP") require a database rebuild.

Impact: In production, you'd need a real-time entity resolution service. For the PoC, it's acceptable — data is static.

6. No Authentication or Multi-Tenancy

The issue: Anyone with access to the server can query all firm data. No RBAC, no audit logging.

Impact: This is a PoC on a laptop — fine for demo. Production would need OAuth2, RBAC, and audit trails.

7. Markdown Output Only

The issue: Pitches are returned as markdown strings. No rich structure, no cite-back to specific matters, no interactive elements.

Impact: Users can copy-paste, but can't click a matter link to see full details. Future versions could return JSON + markdown for richer interactions.

The Three Core Workflows

Workflow 1: RFP-to-Pitch (Flagship)

Goal: Draft a compelling pitch in response to an inbound RFP in ~90 seconds.

Flow:

  1. User pastes RFP into Claude or the web app
  2. Claude calls assemble_pitch_context with the RFP intent
  3. The tool retrieves:
    • ~5 relevant matters (semantic search + structural filters)
    • Top timekeepers with relevant experience
    • Market statistics for the deal type
  4. Claude synthesizes a 2–3 paragraph pitch with:
    • Relevant matter callouts (specific company names)
    • Named timekeepers and their roles
    • Confidence signals (market data, track record)
  5. Output: Markdown pitch, copy-to-clipboard ready

Workflow 2: Timekeeper Bio/CV

Goal: Produce a tailored CV for a named lawyer, scoped to a business opportunity.

Flow:

  1. User asks Claude: "Give me a bio for Jane Smith (our partner) for this healthcare M&A deal"
  2. Claude calls get_timekeeper_history with Jane's name
  3. The tool returns all her matters + roles
  4. Claude filters for healthcare relevance and synthesizes:
    • Title, practice group, years experience
    • 2–3 paragraphs on her healthcare focus
    • Curated matter list with client names and roles
  5. Output: Tailored CV in markdown

Workflow 3: Entity-Resolution Validation ("Wow" Moment)

Goal: Show that the data layer has resolved party name variants into one canonical entity.

Flow:

  1. User asks Claude: "Show me deals where Latham was opposing counsel and we represented the target"
  2. Claude calls search_matters with "Latham" as a filter
  3. The query works because:
    • Splink resolved "Latham", "L&W", and "Latham & Watkins" to one canonical ID
    • The search joins through party_resolution to find all variants
    • Results return in milliseconds (all cached in DuckDB)
  4. Output: Correct matter list, regardless of how counsel was named in the source data

Lessons Learned

1. Make the Architecture Your Ally

By making SQL macros the single source of truth, we eliminated a whole class of bugs (tool drift). The architecture itself enforces correctness. Spend time on the foundation; it pays dividends.

2. Authenticity > Polish

Using real company names and deal structures from SEC EDGAR gave the demo instant credibility. Lawyers trusted the data because it looked like real data. Fake names would have undermined the whole pitch.

3. Two Surfaces, Same Logic

Having both MCP and a web app proved the concept works without being tied to Claude Desktop. It's a platform when you can query it three different ways and get the same answers.

4. Visible SQL Matters

The fact that users can see the SQL behind each tool call became a major differentiator. It's not a black box. It builds trust with technical audiences.

5. MVP Scope Is Hard

Starting with regex markdown rendering seemed pragmatic until edge cases hit. The right move: start with the 80% (headings, emphasis, code) and document when to upgrade (marked.js, noted as tech debt).

6. Embeddings Latency Adds Up

The Python subprocess bridge for embeddings adds 5–10 seconds per query. That's 10% of total latency from one architectural choice. Future versions should port to JavaScript.

7. Documentation Is a Feature

The README, DEMO.md, and this case study are not afterthoughts — they're part of the product. Without them, "aretil" is just code; with them, it's a thinking artifact.

Conclusion

aretil proves that a structured, entity-resolved firm-data layer — exposed as an MCP server — can make Claude dramatically better at business-development tasks.

The key insight: The differentiation is the data layer, not the AI. Claude's drafting is good, but it's only powerful when aimed at structured, entity-resolved data. That's hard. That's the value.

This PoC demonstrates:

  • A pitched RFP can be answered with firm context in ~90 seconds
  • Two visibly different workflows (pitch + bio) run on one shared data layer
  • Entity resolution works: variant names resolve to canonical identities
  • The SQL behind each tool is inspectable — no black box
  • Both MCP and a web API can call the exact same macros — zero drift

The prototype is intentionally narrow (70 matters, synthetic data, no auth) but it's real. A fresh clone builds and runs. The demo script is documented. The workflows are testable. Every architectural decision is explained.

This is not a Claude wrapper. This is a data layer that Claude queries. That's the thesis, and it's proven.
